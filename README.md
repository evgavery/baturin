# Сайт проката AV-оборудования (рабочее название «Screenrent»)

B2B-сайт московской компании проката AV-оборудования: аренда плазменных панелей, LED-экранов, сенсорных панелей и организация видеотрансляций для мероприятий. Цель сайта — не каталог, а инструмент продаж: короткая витрина ходовых позиций и квиз, который за 30 минут доставляет смету в мессенджер клиента.

Единственный источник требований — `TZ-arenda-ekranov.md` (корень репозитория). Архитектурные решения и то, чем реализация осознанно отличается от буквы ТЗ, — в спеке `docs/superpowers/specs/2026-07-28-arenda-ekranov-design.md`. Пошаговый план реализации (для истории и будущих доработок) — `docs/superpowers/plans/2026-07-28-arenda-ekranov.md`. Приёмка этой версии сайта построчно по ТЗ — `docs/superpowers/acceptance-report.md`.

## 1. Разработка

Требования: Node 22 (версия зафиксирована в `.nvmrc`; `nvm use`, если пользуетесь nvm) и PHP 8.1+ в PATH — тесты и локальный стенд поднимают встроенный сервер PHP (`php -S`). На macOS, если `php -v` не находит команду: `brew install php`.

```bash
npm i              # зависимости
npm run fonts      # копирует self-hosted шрифты (cyrillic+latin woff2) в public/fonts/ —
                    # файлы уже закоммичены, но команда идемпотентна и полезна после
                    # обновления пакетов шрифтов (@fontsource-variable/*)
npm run dev         # локальная разработка, http://localhost:4321
```

Полный список команд:

| Команда | Что делает |
|---|---|
| `npm run dev` | Astro dev-сервер с горячей перезагрузкой |
| `npm run build` | продакшн-сборка в `dist/` |
| `npm run check` | `astro check` — типы и диагностика Astro/TypeScript (strict) |
| `npm run fonts` | копирует woff2-шрифты из `node_modules/@fontsource-variable/*` в `public/fonts/` |
| `npm run test:unit` | unit-тесты (vitest) — чистые функции: цены, квиз-логика, LED-калькулятор |
| `npm run test:e2e` | **сначала пересобирает** `dist/` (`astro build`), затем прогоняет Playwright: поднимает `php -S 127.0.0.1:4381 -t dist` сам (см. `playwright.config.ts`) на тестовом конфиге заявок (`tests/fixtures/lead-config.test.php`, `test_mode: true` — заявки не уходят в Telegram/почту, а пишутся в `tests/.tmp/leads.log`) |
| `npm run serve` | поднимает уже собранный `dist/` на `php -S 127.0.0.1:4321` — для ручного просмотра/Lighthouse. Без `LEAD_CONFIG` формы будут искать `lead-config.php` в корне репозитория (на уровень выше `dist/` — так же, как на бою «на уровень выше webroot», см. раздел 2); файл в `.gitignore`, в репозиторий не попадёт |
| `node scripts/check-js-budget.mjs` | бюджет JS ≤ 50 КБ gzip/страницу (ТЗ §12); гонять по свежему `dist/` |
| `node scripts/check-links.mjs` | все внутренние `href`/`src` в `dist/` ведут на реальные файлы; гонять по свежему `dist/` |

Перед коммитом/сдачей — полный прогон:

```bash
npm run check && npm run test:unit && npm run test:e2e \
  && node scripts/check-js-budget.mjs && node scripts/check-links.mjs
```

### `lead-config.php` — конфиг приёма заявок

Файл лежит **вне `src/`**, потому что не собирается Astro — его нужно вручную положить на сервер (раздел 3). Образец — `lead-config.example.php` в корне репозитория:

| Поле | Значение |
|---|---|
| `tg_bot_token` | строка 9 таблицы выше |
| `tg_chat_id` | строка 10 таблицы выше |
| `lead_email` | строка 5 таблицы выше |
| `allowed_origin` | реальный домен сайта, например `https://vash-domen.ru` — заявки с любого другого `Origin`/`Referer` сервер отклоняет (403) |
| `rate_limit_max` / `rate_limit_window` | лимит заявок с одного IP; из коробки — 5 заявок в час (ТЗ §6.4) |
| `test_mode` | **на бою обязательно `false`.** `true` полностью отключает отправку в Telegram/почту — заявки просто пишутся в лог. Используется только для тестов и локальной отладки |
| `test_log` | путь к лог-файлу — используется только при `test_mode: true` |

`lead-config.php` в `.gitignore` — реальный файл с токенами в репозиторий не попадёт, даже если положить его локально для проверки.

## 3. Деплой на Reg.ru

Хостинг — shared-хостинг Reg.ru с PHP, без Node на сервере: сайт собирается локально, на сервер заливается только результат сборки.

1. **Собрать сайт:** `npm run build` → всё содержимое `dist/` (включая `dist/api/lead.php`, скопированный из `public/api/`).
2. **Залить в webroot** (обычно `public_html/` или домен-каталог в файловом менеджере/по FTP панели Reg.ru) — содержимое `dist/`, а не саму папку `dist` (то есть `index.html`, `api/`, `_astro/`, `.htaccess` и т. д. должны лежать прямо в webroot). **`.htaccess` — скрытый файл** (имя начинается с точки): Finder на macOS и часть FTP-клиентов не показывают такие файлы по умолчанию и молча теряют их при копировании — перед заливкой включите отображение скрытых файлов (в Finder: ⌘+Shift+.) и после загрузки проверьте, что `.htaccess` действительно долетел до webroot.
3. **Положить `lead-config.php` НА УРОВЕНЬ ВЫШЕ webroot** — рядом с папкой, в которую распакован `dist/`, а не внутрь неё. Так файл с токенами недоступен по HTTP: `public/api/lead.php` ищет его по пути на два каталога выше себя (`webroot/api/lead.php` → `dirname(__DIR__, 2)`, то есть каталог, содержащий webroot). Скопируйте `lead-config.example.php`, переименуйте в `lead-config.php`, заполните реальными значениями (раздел 2), `test_mode: false`.
4. **В панели Reg.ru включить PHP 8.1 или новее** для домена/сайта (по умолчанию может быть выставлена более старая версия).
5. **Проверить `https` и редирект `www`.** `public/.htaccess` уже содержит правила: принудительный `https` и редирект `www.domain` → `domain`. После первого деплоя:
   - откройте `http://ваш-домен/` (без `s`) — должно редиректить на `https://`;
   - откройте `https://www.ваш-домен/` — должно редиректить на `https://ваш-домен/` (без `www`);
   - откройте `https://ваш-домен/` напрямую и убедитесь, что страница просто загружается, **без** зацикливания редиректов.

   Если браузер показывает «ERR_TOO_MANY_REDIRECTS» — типичная причина на shared-хостингах за прокси/балансировщиком: Apache видит подключение как обычный `http` (`%{HTTPS}` = `off`), даже когда клиент пришёл по `https`, потому что TLS терминируется до Apache, а признак «это был https» приходит только в заголовке `X-Forwarded-Proto`. Правило `RewriteCond %{HTTPS} !=on` тогда истинно всегда → бесконечный редирект на `https`, который сервер считает не-https. Лечится добавлением второго условия (обе строки `RewriteCond` перед `RewriteRule` работают по «И» — редирект сработает, только если ОБА признака говорят «не https»):
   ```apache
   RewriteCond %{HTTPS} !=on
   RewriteCond %{HTTP:X-Forwarded-Proto} !https
   RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [R=301,L]
   ```
   Замените первую пару `RewriteCond`/`RewriteRule` в `public/.htaccess` на этот вариант, если столкнётесь с зацикливанием, пересоберите (`npm run build`) и перезалейте `dist/`.

### Технические проверки после первого деплоя

- [ ] **https и редирект `www`** — см. раздел 3, шаг 5.
- [ ] **Тестовая заявка на боевом конфиге.** После того как в `lead-config.php` вписаны реальные `tg_bot_token`/`tg_chat_id`/`lead_email` и выставлено `test_mode: false` — отправьте одну заявку через любую форму сайта (короткую форму, форму подбора или квиз) и убедитесь, что сообщение действительно пришло в Telegram-чат **и** письмо действительно пришло на `lead_email`. Если Telegram недоступен, `lead.php` всё равно шлёт письмо и пишет в `error_log` сервера — тоже стоит один раз проверить (временно указать заведомо неверный `tg_bot_token`, отправить заявку, убедиться, что письмо всё равно дошло).
- [ ] **Цели Метрики.** Счётчик должен быть уже вписан в `SITE.metrikaId` и сайт пересобран — до этого момента Метрики на странице нет вообще (см. раздел 2, строка 11). В браузере на боевом сайте выполните в консоли `document.cookie = '_ym_debug=1; path=/'` и перезагрузите страницу — Метрика начнёт логировать в консоль каждый хит и каждую цель. Пройдите по сайту и убедитесь, что в консоли появляются все 11 целей ТЗ §10: `quiz_open`, `quiz_step2`, `quiz_step3`, `lead_quiz`, `lead_short`, `lead_qualify`, `click_tg`, `click_wa`, `click_max`, `click_phone`, `calc_use`.
- [ ] **JSON-LD внешним валидатором.** Локально разметка проверена только структурно (парс-тестом — см. `docs/superpowers/acceptance-report.md`): агенту недоступен сетевой доступ к `validator.schema.org`/Google Rich Results Test. После деплоя стоит один раз вручную прогнать боевые `/`, `/plazmy/75/` и ещё одну-две страницы через https://validator.schema.org/ или https://search.google.com/test/rich-results — семантическая проверка (обязательные/рекомендуемые поля по мнению самого Google/Яндекса), а не только «валидный JSON».
- [ ] **Lighthouse на проде.** На локальном стенде (`php -S`) Performance на главной — 87 из-за того, что встроенный сервер PHP не умеет отдавать `Content-Encoding: gzip` для статики (это ограничение стенда, не сайта: тот же `dist/` через сервер с честным gzip даёт 97; подробности и цифры — `docs/superpowers/acceptance-report.md`, пункт про Lighthouse). На проде `public/.htaccess` уже подключает `mod_deflate`, поэтому после деплоя стоит перепроверить: `npx lighthouse https://ваш-домен/ --only-categories=performance,seo,accessibility --output=json` (или просто через PageSpeed Insights в браузере) — ожидаются числа, близкие к прогону с честным gzip, а не к 87.
- [ ] **Длины `title` после замены бренда.** Шаблоны `title` (`src/pages/*.astro`) урезаны в расчёте на бренд длиной примерно до 12 символов (лимит ≤ 60 знаков, ТЗ §9). После того как `SITE.brandName` заменён на реальное название — пересоберите и прогоните `npm run test:e2e`: часть тестов (`tests/e2e/pages.spec.ts` и другие) отдельно проверяют, что `title` каждой страницы не длиннее 60 знаков, и упадут, если новый бренд длиннее «Screenrent» настолько, что какой-то title вышел за лимит. В этом случае — укоротить конкретный шаблон в соответствующем файле страницы.
- [ ] **Ожидания `data.test.ts` после замены цен и парка.** `src/data/data.test.ts` пиннит рыночные цены-ориентиры ТЗ §8.1 и цифры парка (сейчас 250 м² LED и 120 плазменных панелей) точными значениями. После того как в `site.ts` вписаны реальные цены и цифры парка — обновите ожидания в `src/data/data.test.ts` и перегоните `npm run test:unit`.
- [ ] **`npm audit`.** Пакет `astro` закреплён на 5.18.2 (по спеке `docs/superpowers/specs/2026-07-28-arenda-ekranov-design.md`, раздел 3); `npm audit` на этой версии показывает 3 уязвимости (2 high, 1 low) — все они в цепочке зависимостей Astro (esbuild, sharp) и чинятся только апгрейдом до Astro ≥ 7, что ломает совместимость. Для чисто статической сборки без dev-сервера, обращённого в интернет, риск оценён как незначительный. Апгрейд Astro — не срочная, но открытая задача; решение — за Евгением, уже после запуска.

## 5. Дизайн

Источник визуала — дизайн-система из Claude Design (`docs/design_handoff_av_rental_site/`): `README.md` этой папки (токены, типографика, правила bento-сетки, состояния компонентов, поведение) + 5 макетов `*.dc.html` (дизайн-система, главная, `/plazmy/`, `/plazmy/75/`, `/agentstvam/`). Файлы `.dc.html` — референсы поведения и внешнего вида, а не код для копирования; формат `.dc`/`support.js` в проект не переносится.

Все токены (цвета, шрифты, тени, радиусы, отступы) живут в одном месте — `src/styles/global.css`, блок `@theme` — и используются по всему проекту только как Tailwind-классы (`bg-bg`, `text-screen`, `shadow-glow-md`…) или `var(--…)`. Ни одного захардкоженного hex/тени в компонентах. Это значит, что для смены оформления (например, на одну из альтернативных палитр) достаточно поменять значения в `global.css` — переписывать компоненты не нужно.

Альтернативные палитры (Индиго, Стальной, светлая тема) документированы, но не подключены — они описаны в `docs/design_handoff_av_rental_site/README.md`, раздел «Design Tokens». Сайт сейчас — только тёмная тема («Синий зал», акцент `#1E5BFF`); переключалки светлой/тёмной темы нет и не планируется (см. `docs/superpowers/specs/2026-07-28-arenda-ekranov-design.md`, раздел «Вне объёма»).

Расхождения между дизайн-макетами и фактической реализацией (там, где механика/тексты/SEO/цены ТЗ и плана оказались главнее внешнего вида хендоффа) — раздел «Дизайн-хендофф» в `docs/superpowers/plans/2026-07-28-arenda-ekranov.md`.
